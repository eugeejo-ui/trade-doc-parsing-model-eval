# 어떤 고객에게 어떤 모델을 권할 것인가

### 무역금융 서류 파싱 — Granite Docling vs PaddleOCR-VL

신용장 부속서류를 은행 내부 서버에서 읽어낼 파싱 모델 두 개를 동일 조건에서 측정하고,
**어떤 고객 상황에 어느 쪽이 적합한지** 판단 기준선을 측정했다.

결론: 두 모델의 성능은 동일했고, 선택을 만드는 요인은 모델이 아닌 것으로 밝혀졌다.

---

## 결론

**축 1 — 성능**

정형화된 상업 송장 150장에서 금액·날짜·상호 세 필드의 추출 정확도는
두 모델이 동일한 것으로 나타났다.

채점 범위를 페이지 전체로 확장하면 PaddleOCR-VL이 숫자 재현율에서 4.18%p 앞서는
것으로 측정됐다. 다만 Granite가 누락한 항목은 고객 주소와 Tax Id로,
신용장 대조 항목에는 해당하지 않음을 확인했다.

**축 2 — 배포 부담**

Granite Docling 258M(515MB), PaddleOCR-VL 0.9B(1.92GB)으로 모델 크기에
3.5배 차이가 존재한다.

처리 속도는 PaddleOCR이 빠른 것으로 나타났다(18.0초 vs 26.3초, T4 기준).
설계 단계에서는 PaddleOCR이 페이지 단위 파싱을 지원하지 않아 다중 호출이
필요할 것으로 보였으나, 실측 결과 한 번의 호출로 처리됨을 확인했다.

**판단**

> 필드 단위로 추출한다면 258M으로도 충분한 성능을 보일 것으로 나타났다.
> 페이지 전체를 인덱싱하거나 위치 기반 후처리를 수행한다면 0.9B 선택이
> 더 좋은 성능을 보일 것으로 기대된다.
>
> 도입 여부는 모델 성능보다 **운영비가 재제출 비용의 몇 배에 해당하는가**가
> 결정하는 것으로 파악했다.

## 어떤 요인이 도입 여부를 결정하는가

| 요인 | 손익분기에 미치는 영향 |
|---|---|
| **운영비 / 재제출비 비율** | 10배 → 15건, 100배 → 150건 |
| **재제출 1회 비용** | 4배 → 필요 건수 1/4 |
| 모델 탐지율 | 20%p 하락 → 4건 차이 |
| 모델 오탐률 | 20배 증가 → **변화 없음** |

모델의 성능보다 비용 구조가 결정에 더 큰 영향을 끼치는 것으로 나타났다.

### 손익분기

| 월 운영비 (재제출 M건 값) | 손익분기 |
|---|---|
| 5 | 8건 |
| 10 | 15건 |
| 50 | 75건 |
| 100 | 150건 |

재제출 1회 비용에는 재작성 인건비뿐 아니라 은행 재심사 대기 5영업일(UCP 600)의
기회비용이 포함됨을 명시한다. 5영업일 지연이 자금 회전에 치명적인 중소 수출기업일수록
손익분기가 낮아지는 것으로 확인했다.

설계 단계에서는 "오탐 확인 부담이 절감을 상쇄한다"고 예상했으나,
오탐률을 2.5%에서 50%로 20배 상향해도 손익분기가 변하지 않음을 확인했다.
이는 오탐 확인 비용이 재제출 비용에 비해 자릿수가 작기 때문인 것으로 파악했다.
절감을 상쇄하는 요인은 오탐이 아니라 **고정 운영비**인 것으로 나타났다.

## 판단 절차

규칙을 먼저 검증하고, 검증된 규칙으로 모델 측정을 진행했다.

**1. 규칙의 정확성 사전 확인**

BPI Challenge 2019 실데이터 8,564건으로 금액 대조 규칙을 검증했다.
규칙 출력이 정의상 정답과 100% 일치했으며, 허용오차를 0.001~10 EUR로 변경해도
판정이 변하지 않음을 확인했다.

**2. 정답지의 사전 확정**

조건별 정답지 9종을 생성해 파일로 고정한 뒤 모델을 실행했다.
이는 결과를 확인한 이후 정답을 수정할 여지를 제거하기 위한 조치임을 명시한다.

**3. 동일 조건에서의 모델 실행**

동일한 150장을 동일한 순서로 실행했다.
프롬프트는 양쪽 5개씩 비교해 최선값을 채택했다.

**4. 단일 추출기를 통한 채점**

모델별 파서를 별도로 작성할 경우 파서 품질 차이가 결과에 혼입되기 때문임을 명시한다.

**5. 검증된 규칙 적용 및 탐지율 환산**

**6. 탐지율의 비용 수식 대입**

## 공정성을 확보한 방법

두 모델의 출력에 **동일한 추출기 하나**를 적용했다.

PaddleOCR 프롬프트로 `Table Recognition:`을 선택한 것도 Granite와 동일한
OTSL 태그 체계를 확보하기 위해서임을 명시한다.
값의 정확도가 아니라 출력 형식을 선택 기준으로 삼았다.

Granite는 프롬프트에 따라 표 셀 추출 결과가 0개와 40개로 갈리는 것으로 나타났다.
`Convert this page to docling.`에서는 표가 빈 상태로 출력됐고,
`Convert this page to OTSL.`에서 40셀이 채워짐을 확인했다.

### 추출기 수정 이력

| 문제 | 영향 | 수정 |
|---|---|---|
| 우편번호를 금액으로 오인 | Granite | 소수점 두 자리 필수화 |
| 군사우편 주소 절단 실패 | 양쪽 43건 | 주소 키워드 추가 |
| `Seller:`와 이름이 한 칸에 위치 | PaddleOCR | 접두사 처리 경로 추가 |

둘 중 하나의 모델만 판정 결과가 불리해지는 규칙은 채택하지 않았다.
각 수정 이후 양쪽 점수 변화를 기록했다.

| 단계 | Granite 상호 | PaddleOCR 상호 |
|---|---|---|
| 초기 | 84.0% | 85.3% |
| 주소 키워드 추가 후 | 98.0% | 96.0% |
| Seller 접두사 처리 후 | **100.0%** | **100.0%** |

## 결과

### 필드별 추출 정확도 (n=150)

| | 금액 | 날짜 | 상호 |
|---|---|---|---|
| Granite Docling | 98.0% | 100.0% | 100.0% |
| PaddleOCR-VL | 98.0% | 100.0% | 100.0% |

금액 오답 3건은 두 모델이 동일한 값을 산출했다. 해당 건은 정답 JSON의 `total`이
세후가 아닌 세전 금액으로 기재된 경우로, 데이터셋 표기 불일치에 해당하며
모델 오류가 아님을 확인했다. 정답지는 수정하지 않았다.

### 하자 탐지율

탐지율 100%, 오탐률 2.5%로 두 모델이 동일했다.
9개 조건 전부 차이가 0.0%p로 나타났다.

주입 폭을 0.1%에서 50%로 500배 확대해도 탐지율이 변하지 않았다.
기한 조건도 1일에서 30일까지 동일했다.
탐지율은 하자 크기가 아니라 파싱 정확도에 의해 결정되는 것으로 파악했다.

### 페이지 전체 인식 (보조 지표)

| | 숫자 재현율 (순서 무시) |
|---|---|
| Granite | 79.06% |
| PaddleOCR | 83.25% |

초기 측정에서 17.85%p 차이가 나타났으나, 이 중 13.67%p는 **읽기 순서**에서
비롯된 것으로 확인했다. Granite는 고객 주소 블록을 출력 말미에 배치하는 반면
정답 텍스트는 시각적 읽기 순서를 따르므로, 순서 기반 비교에서 Granite가
일방적으로 불리해지는 구조임을 명시한다. 순서를 무시한 다중집합 비교로
재측정한 결과 차이가 4.18%p로 축소됨을 확인했다.

Granite가 누락한 항목은 Tax Id·우편번호·번지수로 전부 고객 주소 영역에
해당했다. 금액·품목 수량·날짜에서는 누락이 발견되지 않았다.

## 전제

- 고객: 신용장 업무를 취급하는 은행
  (외국환거래법상 증권사는 지급·추심 업무를 취급하지 못함)
- 배포: 은행 내부 서버. 외부 API 호출 방식이 아님
- 검증 대상: 파싱 기반 모델. 완성 시스템이 아님
- 비교: 사람 점검(AS-IS) 대 AI 도입(TO-BE)
- 범위 밖: 이미 동일 업무를 자동화한 기관의 솔루션 교체

## 한계

**데이터**

- 정형화된 합성 송장이며, 손글씨·스캔 노이즈·비정형 레이아웃은 포함되지 않음
- 일반 상업 인보이스이며 신용장 부속 상업송장이 아님을 명시한다
- 표본 150장은 1~2%p 차이를 변별하기에 충분하지 않음
- 금액 표기가 점 소수점(1,078건)과 쉼표 소수점(336건)으로 혼재함을 확인했다

**하자율**

- ICC가 보고한 70%는 **1차 제시 거절률**이며 최종 지급거절률이 아님을 명시한다
- 이미 사람이 점검한 이후의 수치임을 명시한다

**조건 합성**

- 선적일 필드가 존재하지 않아 발행일을 대조 대상으로 사용했다
- 마감일은 UCP 600 제14조(c)의 21일 제시기간을 기준으로 합성함을 명시한다
- UCP 600 엄격일치 원칙은 1일·1원 차이도 하자로 규정하나, 파싱 정확도를
  분리해 측정하기 위해 완화된 조건을 적용함을 명시한다

**비용 계산**

- 재제출 비용과 운영비의 절대 금액은 공개 자료가 존재하지 않으므로 확인할 수 없음
- 두 값의 비율로 환원했을 뿐 불확실성이 제거된 것은 아님을 명시한다
- 오탐이 많을 경우 담당자가 시스템을 신뢰하지 않아 사용하지 않게 될 수 있으며,
  이는 비용이 아니라 채택의 문제이므로 수식에 반영되지 않음을 명시한다

**규칙 검증**

- 금액 규칙만 외부 실데이터로 검증했다
- 기한·명칭 규칙은 BPI 2019에 대응 필드가 존재하지 않으므로
  검증을 진행하지 못함을 명시한다

**실행 환경**

- Tesla T4 단일 GPU, 배치 처리 미적용
- A100/H100에서는 절대 시간이 달라짐

## 재현

```bash
pip install -r requirements.txt

python src/run_bpi_check.py      # 0단계: 규칙 검증
python src/inspect_kaggle.py     # 1단계: 스키마 파악
python src/make_truth.py         # 1.5단계: 정답지 생성
# 2~3단계: Kaggle 노트북 (notebooks/ 참조)
python src/score.py              # 4단계: 채점
python src/detect.py             # 5단계: 탐지율
python src/text_accuracy.py      # 5b단계: 문자 정확도
python src/breakeven.py          # 6단계: 손익분기
```

원본 데이터는 용량상 포함하지 않았음을 명시한다. 아래 출처에서 받는다.
단계별 설계와 판단 근거는 [`docs/`](docs/)에 정리했다.
