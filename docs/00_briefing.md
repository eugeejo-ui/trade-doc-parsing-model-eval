**따라서 산출물은 벤치마크 비교표가 아니라 "조건별 판단 기준선"입니다.**

## 3. 주제와 시장 맥락

### 주제

**무역금융 서류 파싱 — 은행 내부에 깔 수 있는 모델은 어디까지 읽어내나**

### 왜 이 주제인가 (딜로이트 「아태 금융서비스 산업의 미래」 2026.9.14)

- 공급망 재편으로 **무역금융·거래은행 수요가 빠르게 증가**
- 아태 중소·영세기업 **최대 2조 7,000억 달러** 자금조달 격차.
  은행은 담보 충분한 기업에 적합한 구조라 **자산 적은 제조 혁신기업 지원이 부진**
- → **제조(수출기업)가 서류를 쓰고 → 금융(은행)이 그 서류로 판단**하는 구조.
  하나의 문서를 사이에 두고 두 산업이 마주 봄

### 왜 자체 배포 모델인가 (같은 보고서 4장)

- **금융회사 80%, 아태 87%가 AI 공급업체 선정 시 출신 국가를 고려**
- 기술주권은 **모델 출처, 컴퓨팅 위치, 알고리즘 투명성**까지 확대
- 가트너: **정부 65%가 2028년까지 기술주권 요건 도입** 전망
- **아태 금융범죄 규제 준수 비용 연 450억 달러**, 상당 부분이 인력 집약 프로세스
- 단, 보고서는 "기술주권 = 완전한 독립이 아니며 **신뢰할 수 있는 파트너십**이 유리"라고
  선을 그음 → 이게 IBM의 자리

### 실증 사례 (성격 주의)

하나은행 **'비대면 AI 수출서류작성 가이드'** (2026.3.25, 금융권 최초)

- **은행이 심사를 자동화한 것이 아님.** 수출기업이 서류를 내기 **전에**

## 5. 실험 설계 (확정)

### 비교 대상 — **2층만 비교**

| | Granite Docling | PaddleOCR-VL-1.6 |
|---|---|---|
| 하는 일 | 레이아웃 파싱 → 구조화 JSON | 동일 |
| 크기 | 258M | 0.9B |
| 개발사 | IBM (미국) | 바이두 (중국) |
| 기반 | Granite 자체 | ERNIE-4.5 |
| 라이선스 | Apache 2.0 | Apache 2.0 |
| 벤치마크 | 상위권 아님 | **OmniDocBench v1.6 1위 96.33%** |

**Claude는 경쟁자가 아니라 성능 천장을 보여주는 눈금.** 자체 배포 불가라 선택지가 아님.

### 3층은 모델이 아니라 규칙으로 처리

```python
if invoice.amount != lc.amount:            → 금액 불일치
if invoice.ship_date > lc.latest_date:     → 기한 초과
if invoice.beneficiary != lc.beneficiary:  → 명칭 불일치
```

이유 2가지:

1. **공정성** — Granite Vision은 Docling과 긴밀히 연동되도록 설계됐고
   Docling은 DocTags 자체 형식을 씀. 3층에 Granite Vision을 두면
   "IBM 조합이 서로 잘 맞아서" 이긴 건지 구분 불가
2. **기능 비대칭** — PaddleOCR의 KVP 담당은 PaddleOCR-VL이 아니라 **PP-ChatOCRv4**.
   이건 단일 모델이 아니라 PP-Structure + 벡터DB + ERNIE-4.5-300B + 융합 단계로 된
   RAG 파이프라인. Granite Vision 4B와 직접 비교 불성립

**Granite Vision 4.1은 이번 실험에서 제외.**

### 데이터

| | 케이스 1 (본체) | 케이스 2 (여유 시) |
|---|---|---|
| 출처 | **Kaggle: High Quality Invoice Images for OCR** | FraudRAG-2400 (IEEE DataPort) |
| 규모 | 8,181장 중 **1,489장 구조화 JSON 정답** | 2,400건 (정상 1,600 / 이상 800) |
| 측정 | **파싱 정확도** | 판단 로직 검증 |

케이스 1은 정답 JSON이 이미 있어 **하자를 주입하지 않아도 파싱 정확도가 바로 나옴.**
FraudRAG는 **무역서류가 아님**(은행·카드·급여·투자·모기지·세무).
쓴다면 "유형이 겹쳐 판단 로직 검증용으로 썼다"고 반드시 명시.

### 측정 2단계

1. **필드별 추출 정확도** (정답 JSON 대조)
2. **규칙 대조 후 하자 탐지율로 환산**
   → 파싱이 틀리면 대조가 틀리고, 하자를 놓침. 파싱 정확도가 탐지율로 환산됨

## 6. 비용 수식 (검증 완료)

### 변수

| 기호 | 의미 | 출처 |
|---|---|---|
| N | 월 서류 건수 | 입력 |
| d | 하자 발생률 (기본 0.7) | ICC |
| t_w / t_c | 작성 / 자가점검 시간 | 입력 |
| t_f / t_v | 수정 / 오탐 확인 시간 | 입력 |
| R | **재제출 1회 비용** | 입력 |
| r / p | **탐지율 / 오탐률** | **실험** |
| C | AI 운영 비용 | 고정 |

```
AS-IS = N × (t_w + t_c) + N × d × R

TO-BE = N × (t_w + t_c')
      + N × d × r × t_f          AI가 잡은 하자 → 수정
      + N × (1-d) × p × t_v      오탐 확인
      + N × d × (1-r) × R        놓친 하자 → 재제출
      + C

절감 = N×d×r×R − N×d×r×t_f − N×(1-d)×p×t_v − C
```

- **R이 지배 변수.** 재작성 + 은행 재심사 대기(UCP 600상 최대 5영업일)라
  t_f·t_v와 자릿수가 다름. 탐지율 r이 1%p 오르면 N×d×R×0.01 절감
- **d=0.7은 이미 사람이 점검한 뒤의 값.** 사람 점검 항을 따로 빼면 이중 차감
- **회사 규모 데이터는 구할 수 없음**(개별 기업 신용장 건수 비공개).
  규모로 나누지 말고 **입력값으로 받을 것**

## 9. 결론의 두 축

**축 1 — 성능**

> 파싱 정확도 차이 N%p, 규칙 대조 후 탐지율 차이 M%p

**축 2 — 배포 부담**

> PaddleOCR은 파싱 담당이고 필드 추출까지 가려면
> PP-ChatOCRv4(벡터DB + ERNIE-4.5-300B)가 필요하다.
> Granite는 Docling 258M으로 파싱을 덮는다.

최종 문장의 형태:

> **"파싱만 필요하면 PaddleOCR-VL. 필드 추출까지 한 스택으로 내부에 넣어야 하면 Granite."**
> **"월 N건 이상이면 Granite 탐지율로도 손익분기를 넘는다. 그 이하면 오탐 확인 부담이 절감을 먹는다."**
