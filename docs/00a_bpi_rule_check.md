### 왜 이 데이터인가

3-way matching(주문·입고·송장 3자 대조)이 데이터 설계의 핵심이며,
신용장 심사가 세 문서를 조건과 대조하는 구조와 **연산이 같다**.

### 한계 (README 명시 대상)

- **무역서류가 아니다.** 기업 내부 구매-지급 프로세스 로그
- **금액 규칙 1종만** 검증 가능

- **정답 라벨이 없다.** 단, 3자 대조는 정의가 결정적이라 정답을 계산으로 구할 수 있음

## 3. A 방법 — 단순 케이스

### 3.1 필터

| 단계 | 조건 | 잔존 |
|---|---|---|
| 전체 | — | 251,734 |
| 3-way 대상 | `GR-Based Inv. Verif.`=True AND `Goods Receipt`=True | 15,182 |
| 분할 제외 | PO·GR·INV 각 1회 | 8,571 |
| 0원 제외 | `abs(PO) > 1` | **8,564** |

**제외율 43.6%**

### 3.2 분할 납품을 제외한 이유

금액 컬럼이 `Cumulative net worth (EUR)` — 누적값이다.

```
1차 입고 → 30만
2차 입고 → 70만   (40만이 아니라 누적)
3차 입고 → 100만
```

공식 문서상 임대료는 12회, 물류 서비스는 **수백 회** 입고가 발생한다.
실측 최대: 입고 269회 / 송장 279회.

입고-송장 짝짓기는 BPI 챌린지 공식 과제 중 하나이므로 범위 밖으로 둔다.

### 3.3 판정

```python
amount_matches(PO, GR, INV, eps=0.01)
```

## 4. 결과

### 4.1 규칙 검증 — 통과

| 항목 | 값 |
|---|---|
| 대상 | 8,564건 |
| **규칙 vs 정의상 정답** | **100% 일치** |
| 불일치 판정 | 164건 (1.91%) |

3자 대조는 정의가 결정적이므로 정답을 직접 계산해 규칙 출력과 대조했다.
한 건도 어긋나지 않았다 → **구현에 버그 없음**

### 4.2 허용오차(ε) 민감도

| eps (EUR) | 불일치 | rel | 불일치 |
|---|---|---|---|
| 0.001 | 164 | 5% | 164 |
| 0.01 | 164 | 10% | 164 |
| 0.1 | 164 | | |
| 1.0 | 164 | | |
| 10.0 | 164 | | |

**전 구간 불변.** 금액 차이가 "정확히 0" 아니면 "매우 큼"으로 갈려 있기 때문이다.
0이 아닌 최소 차이가 13 EUR이고, 그마저 해당 건 PO의 650%였다.

→ **ε를 자의적으로 고르지 않았다**는 근거.
→ 신용장 허용범위(±5%)를 이식하지 않는다. 다른 제도의 규칙이며, 넣어도 결과가 같다.

### 4.3 재작업 교차확인 — 예상과 반대

|  | 재작업 있음 | 재작업 없음 |
|---|---|---|
| 규칙=불일치 | 8 | 156 |
| 규칙=일치 | 2,570 | 5,830 |

```
불일치 건 중 재작업 :  4.9%
일치   건 중 재작업 : 30.6%   ← 6배
```

대조 활동 6종: `Remove Payment Block`, `Change Quantity`, `Change Price`,
`Cancel Invoice Receipt`, `Vendor creates debit memo`, `Cancel Goods Receipt`

**해석**: 재작업은 하자의 증상이 아니라 **치료**다.
`Change Price`가 발생한 건은 값이 고쳐져 최종적으로 일치한다.
규칙이 잡은 164건은 **아무도 손대지 않아 끝까지 어긋난 채 남은 건**이다.

| | 의미 |
|---|---|
| 재작업 있음 + 일치 | 어긋났다가 **고쳐진** 건 |
| 재작업 없음 + 불일치 | 어긋난 채 **방치된** 건 |

→ 원래 설계한 "교차 검증"으로는 성립하지 않는다. 보완 관계로 해석해 기재한다.

### 4.4 미정산 제외

|  | 미정산 | 정산완료 |
|---|---|---|
| 규칙=불일치 | 36 | **128** |
| 규칙=일치 | 1,249 | 7,151 |

`Clear Invoice`가 없는 36건은 거래 진행 중이라 "덜 받은 것"이지 하자가 아니다.

**최종 하자 후보 128건**

### 4.5 하자 패턴 — 무작위가 아님

| 유형 | 형태 | 건수 |
|---|---|---|
| 유형 1 | 주문=송장, **입고만 어긋남** | 42 (33%) |
| 유형 2 | 입고=송장, **둘 다 주문과 어긋남** | 16 (12%) |
| 기타 | | 70 |

배수 분포:

```
GR/PO = 2배  20건
        3배   3건
        4배   2건
정수배 합계  29건 / 128건
```

반올림이나 오타라면 정수배가 나오지 않는다.
**중복 기록 성격의 체계적 원인**으로 보인다.

- 유형 1 — 청구는 맞는데 입고 장부만 부풀려짐 → 장부 오류
- 유형 2 — 주문보다 많이 받고 그만큼 청구까지 됨 → 실제 지출 초과

예시:

| 케이스 | PO | GR | INV |
|---|---|---|---|
| 4507005791_00001 | 19 | 38 | 19 |
| 4507008286_00001 | 114 | 228 | 114 |
| 4507009284_00010 | 24,551 | 49,103 | 49,103 |

## 6. 하지 않은 것

- **측정된 1.91%를 브리핑 6번의 `d`로 쓰지 않는다.**
  `d=0.7`은 신용장 1차 제시 거절률(ICC)이고, 1.91%는 기업 내부 구매 프로세스 수치다.
  제도가 다르므로 치환하면 안 된다.
- 프로세스 마이닝 분석(모델 발견, 변이 분석)은 수행하지 않는다.
  범위를 넘기면 프로젝트 주제가 흐려진다.
- 128건 자체를 성과로 내세우지 않는다. **규칙이 동작한다는 근거**로만 쓴다.

## 7. B 방법 (보류)

분할 납품 건을 누적값의 **마지막 값**으로 복원해 표본을 확장한다.

```
입고 3회 → 30만 / 70만 / 100만
                        ↑ 총 입고액
```

**필수 조건**: `Clear Invoice`가 있는 건만 사용.
없으면 진행 중인 건이 "금액 부족"으로 오탐된다.

**판단**: 결론을 바꾸지 않고 표본만 늘린다.
마감(9/27) 대비 케이스 1이 우선이므로 **후순위**로 둔다.
