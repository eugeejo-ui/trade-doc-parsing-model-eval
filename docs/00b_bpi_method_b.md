# 0단계 B 방법 — 분할 납품 건 확장

**상태**: 폐기 (2026-09-22)
**선행**: A 방법 완료 (8,564건 / 128건 / 규칙 100% 일치)
**소요**: 약 1시간

---

## 1. 목적

A 방법에서 **43.6%를 제외**했다. 이 중 상당수는 분할 납품 건이며,
누적값의 성질을 이용하면 복원할 수 있다고 보았다.

**목적은 결론 변경이 아니라 표본 확대와 제외율 축소였다.**
A 방법의 결론(규칙이 정의상 정답과 100% 일치)은 이미 확정된 상태였다.

---

## 2. 원리 (가설)

금액 컬럼이 `Cumulative net worth (EUR)` — 이름상 누적값이다.
따라서 마지막 이벤트의 값이 곧 총액일 것으로 가정했다.

```
입고 3회 → 30만 / 70만 / 100만
                        ↑ 총 입고액
```

A 방법이 "1회짜리만" 본 것을, B는 "마지막 값"으로 확장한다.

> 이 가설은 4절과 9절에서 반증된다.

---

## 3. 필수 조건 — `Clear Invoice`

**이 조건이 없으면 B는 성립하지 않는다.**

```
100만 주문 → 70만까지만 입고 → 로그 종료
                    ↑
        "덜 받은 것"이 "금액 부족"으로 오탐됨
```

`Clear Invoice`(송장 정산 완료)가 있는 건만 사용한다.
정산이 끝났다는 것은 거래가 완결됐다는 뜻이므로,
남은 차이는 미완이 아니라 진짜 불일치다.

A 방법에서도 이 조건이 필요했음이 확인됐다 (164건 → 128건).

---

## 4. 제외 대상

| 제외 | 사유 |
|---|---|
| `Clear Invoice` 없는 건 | 거래 미완결 |
| 입고 횟수 상위 건 | 입고-송장 짝짓기 필요, BPI 공식 과제 범위 |
| PO 금액 0원 | A와 동일 |

입고 횟수 상한은 95퍼센타일인 21회로 설정했다.

## 9. 실행 결과 — 폐기 (2026-09-22)

**중단 조건 해당: 누적값 해석이 데이터와 맞지 않음**

### 9.1 증상

```
[5] 규칙 vs 정의상 정답 : 100% 일치
    불일치 판정         : 983건 (49.52%)
    (A 방법 비교        : 128건 / 1.50%)
```

A 대비 **33배**. 983건 중 **496건이 주문액의 정수배**.
하자가 절반에 달하면서 이렇게 규칙적인 배수가 나오는 일은 없다.

출력 예시:

| 케이스 | PO | GR | INV |
|---|---|---|---|
| 2000000030_00001 | 549 | 549 | **1,098** |
| 4507000322_00040 | 8,939 | 8,939 | **17,878** |
| 4507000444_00010 | 481,965 | 481,965 | **963,930** |

주문과 입고는 같은데 송장만 정확히 2배 — 계산 착오의 모양이다.

### 9.2 1차 진단의 오류 (자체 정정)

최초에 타임스탬프로 정렬했으나, 로그에는 **`eventID` 컬럼**이 있고
케이스 내에서 연속된 정수로 실제 이벤트 순서를 담고 있다.

```
4507000322_00040
  2881923055616  Create Purchase Order Item
  2881923055617  Change Quantity
  2881923055618  Record Goods Receipt
  ...            ← 연속
```

타임스탬프 동률이 B 대상의 **36.1%**(767/2,127)에 달해 `.last()`가 자의적이었다.

→ **정렬 기준 선택이 잘못됐다. `eventID`를 썼어야 했다.**

1차 보고에서 "입고 값이 전부 동일(64.4%)해서 누적이 아니다"라고 적었으나
이 역시 잘못된 측정이었다. 아래 재검증으로 대체한다.

### 9.3 재검증 — 순서를 바로잡아도 복원 불가

`eventID` 순으로 다시 측정했다.

**입고 값의 누적 여부**

| 항목 | 결과 |
|---|---|
| 다회 입고 케이스 | 4,245건 |
| 단조 비감소(누적 가능) | 38.3% |
| 엄격 증가(확실히 누적) | 5.7% |
| **비단조(뒤섞임)** | **61.7%** |

실제 시퀀스:

```
4507000469_00001: [1420, 639, 1420, 1847, 568, 639, 71, 319, 355, ...]
4507000473_00001: [8786, 76675, 37551, 27654, 21088, 22012, ...]
4507000471_00001: [627, 4081, 4709]
```

**값이 오르내린다. 누적값은 감소하지 않는다.**
이 값은 누적 합계가 아니라 **회차별 입고 금액**이다.

**총액 복원 시도**

| 가설 | 결과 |
|---|---|
| `last(GR) == PO` | 36.5% |
| `sum(GR) == PO` | **0.0%** |
| (대조) 단회 입고 `GR == PO` | **95.1%** |

마지막 값으로도, 합계로도 주문액이 복원되지 않는다.
합계는 **한 건도 맞지 않았다**.

반면 **값이 하나뿐인 단회 입고에서는 95.1%가 일치**한다.
A 방법이 성립하고 B가 성립하지 않는 이유가 여기에 있다.

### 9.4 근본 원인

```
4507000471_00001
  주문 313
  입고 [627, 4081, 4709]
```

주문 313에 입고가 수천 단위다. 자릿수부터 다르다.
이 컬럼이 품목 단위가 아닌 **다른 집계 기준을 섞어 담고 있을 가능성**이 있다.

공식 문서(ICPM 2019 BPI Challenge 페이지)에 이 컬럼의 정의가 명시돼 있지 않다.
더 파고들면 추측이 되므로 여기서 멈춘다.

입고-송장 대응 관계를 푸는 것은 **BPI 챌린지 공식 과제 2번**이다.

> 송장 처리 프로세스의 처리시간은 얼마인가. 한 라인 품목에 여러 입고 메시지와
> 여러 송장이 있을 때, 이들이 어떻게 관련되고 어느 것끼리 짝인지 맞추는
> 기법이 필요하다.

본 프로젝트 범위를 벗어난다.

### 9.5 교훈 — `[5] 100% 일치`의 함정

B 실행에서 규칙 검증은 **통과**했다. 그런데 결과는 틀렸다.

```
전처리가 틀린 숫자를 만들어냄
        ↓
규칙 함수는 그 틀린 숫자를 정확히 비교함
        ↓
"규칙 vs 정의상 정답 100% 일치" 통과
```

규칙 검증 통과는 **함수가 주어진 숫자를 올바르게 비교했다**는 의미일 뿐,
**그 숫자가 올바르게 추출됐다**는 보장이 아니다.

A 방법에서는 값이 단일이라 추출 오류의 여지가 없었기에 이 함정이 드러나지 않았다.

**검증의 범위를 정확히 아는 것이 검증 자체보다 중요하다.**

### 9.6 조치

B 폐기. 0단계는 **A 결과로 확정**한다.

| | 상태 |
|---|---|
| A 방법 8,564건 / 128건 / 규칙 100% 일치 | **확정** |
| B 방법 | **폐기** |

`rules.py`의 `amount_matches()` 검증 상태는 A 결과에 근거하며,
B의 실패는 규칙이 아니라 **전처리의 실패**이므로 검증 결론에 영향을 주지 않는다.
