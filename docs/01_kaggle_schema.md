## 4. 규칙 3종 대응 — 실측 결과

| 규칙 | 모델이 읽을 값 | 채움 비율 | 대조 조건 | 판정 |
|---|---|---|---|---|
| `amount_matches` | `subtotal.total` | **100.00%** | 합성 | **성립** |
| `name_matches` | `invoice.seller_name` | **100.00%** | 합성 | **성립** |

| (참고) | `invoice.due_date` | **0.00%** | — | 사용 불가 |

세 규칙 모두 구조가 같다.

```
모델이 읽은 값        vs        우리가 만든 조건
  ↑ 이미지에서                    ↑ 합성
```

### 4.1 기한 규칙 조정

**선적일(ship date)이 없다.** 날짜는 `invoice_date`와 `due_date`뿐이며,
`due_date`는 **전 건이 비어 있다.**

| 안 | 내용 | 판정 |
|---|---|---|
| A | 발행일을 선적일로 대체 | 부적합. 의미가 다름 |
| **B** | **발행일을 대조 대상, 마감일은 합성** | **채택** |
| C | 기한 규칙 제외 | 불필요 |

발행일 파싱 성공률 100%, 기간은 2011-05-31 ~ 2021-05-30이다.

### 4.2 마감일 설정 근거

| | 값 | 근거 |
|---|---|---|
| **마감 간격** | 발행일 + **21일** | **UCP 600 제14조(c)** — 선적일로부터 21일 이내 제시 |
| 데이터 교차확인 | **불가** | `due_date`가 전 건 비어 있음 |

교차확인은 못 했으나, 21일은 이 프로젝트가 다루는 규정 자체에서 온 값이므로
데이터에서 뽑은 값보다 근거가 강하다. 그대로 사용한다.

## 5. 하자 주입 설계

### 5.1 하자율 `d = 0.7`이란

**신용장 서류를 은행에 내면 10건 중 7건이 1차 제시에서 거절된다**는 수치다.

- 출처: ICC 은행위원회 선임기술자문 **Dave Meynell**, 1차 제시 거절률 **65~80%**
- 원인: UCP 600의 **엄격일치**. 단수/복수 차이, 단가 1센트 차이로도 거절

**반드시 구분할 것 (브리핑 11절)**

| | |
|---|---|
| 1차 제시 거절률 | 70% ← 이 값 |
| 최종 지급거절률 | 훨씬 낮음. 대부분 고쳐서 재제시하면 통과 |

**이미 사람이 점검한 뒤의 값이다.**
비용 수식에서 사람 점검 항을 따로 빼면 이중 차감이 된다 (브리핑 6절).

**쓰이는 곳 두 군데**

```
1.5단계 정답지 → 1,413장 중 70%(989건)에 하자 주입
6단계 비용     → 월 서류 중 70%에 하자가 있다고 놓고 절감액 산출
```

> 0단계에서 측정된 1.91%는 기업 내부 구매 프로세스 수치이므로 사용하지 않는다.
> 제도가 다르다.

### 5.2 통화 자릿수 ★

정답 JSON의 금액은 **소수점 둘째 자리까지** 표기된다.
합성 조건 금액도 **같은 자릿수로 반올림한다.**

반올림하지 않으면 송장값과 조건값이 항상 미세하게 달라져
**모델이 완벽히 읽어도 전건이 하자로 판정된다.**

```
반올림 안 함: 송장 1.71  vs  조건 1.71171  →  항상 다름  →  전건 하자
반올림 함   : 송장 1.71  vs  조건 1.71     →  같음       →  정상
```

실제 신용장 조건에도 `1.71171` 같은 값은 기재되지 않는다. 통화 단위까지만 쓴다.

```python
CURRENCY_DP = 2   # 통화 소수 자릿수. 정답 JSON이 둘째 자리까지 표기함
```

날짜는 일 단위이므로 동일한 성격의 제약을 이미 갖는다. 별도 처리 불필요.

### 5.3 금액 표기 형식 — 파싱 오류와 정정 ★

이 데이터셋의 금액 표기는 **두 가지 형식이 섞여 있다.**

| 형식 | 건수 | 예 |
|---|---|---|
| 점이 소수점 | 1,078 | `232.95` `3 838.87` |
| **쉼표가 소수점** | **336** | `360,58` `70 577,35` |

- 천 단위 구분은 **공백**이다
- 점과 쉼표가 한 값에 함께 나오는 경우는 **0건**

#### 발생한 오류

초기 파싱 코드가 쉼표를 잡음으로 보고 제거했다.

```python
str.replace(r"[^0-9.\-]", "", regex=True)   # 쉼표 삭제
```

| 입력 | 잘못된 결과 | 실제 값 |
|---|---|---|
| `3 838.87` | 3838.87 | 3838.87 ✓ |
| `360,58` | **36058.0** | 360.58 (100배) |
| `70 577,35` | **7057735.0** | 70577.35 (100배) |

**336건의 금액이 100배로 부풀려졌다.**
모델 실행 전에 발견해 수정했다. 실행 후였다면 전 결과를 폐기해야 했다.

#### 수정 후 파싱 규칙

```python
def parse_amount(s):
    """천 단위 구분 = 공백. 소수점 = 점 또는 쉼표 (건마다 다름)."""
    t = re.sub(r"[\s\u00a0\u202f]", "", str(s))
    if "," in t and "." in t:
        t = (t.replace(".", "") if t.rfind(",") > t.rfind(".")
             else t.replace(",", "")).replace(",", ".")
    else:
        t = t.replace(",", ".")
    return float(t)
```

#### 수정 전후 분포

| | 수정 전 (오류) | **수정 후** |
|---|---|---|
| 최소 | 1.71 | **1.09** |
| 25% | 233.31 | **210.80** |
| 중앙값 | 1,020.16 | **692.78** |
| 75% | 23,823.05 | **5,013.80** |
| 최대 | **19,452,170.00** | **194,521.70** |
| 평균 | 436,292 | **7,844.66** |
| 평균/중앙값 | **400배** | **11배** |

수정 전 최대값 19,452,170은 **실재하지 않는 값**이었다.
초기에 "금액 분포가 극단적"이라 판단했으나 파싱 오류의 산물이었고,
수정 후 분포는 상업 인보이스로 자연스럽다.

### 5.4 금액 주입은 비율로

```
절대값 주입: "100원 차이" → 소액은 배수 차이, 고액은 티도 안 남
비율 주입  : "10% 차이"  → 어느 금액이든 같은 난이도
```

**비율로 주입한다.** 최소값이 1.09로 0이 없어 나눗셈 오류 우려도 없다.
방향은 **증가·감소 반반**으로 섞는다. 한쪽으로만 틀리면 모델이 방향을 학습할 여지가 생긴다.

### 5.5 판정 기준과 출제 난이도는 다른 문제

```
판정 기준   → UCP 600 엄격일치. 1일·1원 차이도 하자  (외부 규정)
출제 난이도 → 몇 일 / 몇 % 차이로 문제를 낼 것인가    (우리가 결정)
```

1일·1원 차이로만 출제하면 모델이 한 자리 잘못 읽는 것만으로 판정이 뒤집혀,
**"못 읽어서"인지 "차이가 작아서"인지 구분되지 않는다.**
반대로 너무 크게 잡으면 모델 간 차이가 드러나지 않는다.

0단계에서 ε를 다룬 방식을 그대로 적용해 **여러 단계를 전부 측정한다.**

| 규칙 | 주입 단계 |
|---|---|
| 금액 | 0.1% / 1% / 10% / 50% |
| 기한 | 1일 / 3일 / 7일 / 30일 |
| 명칭 | 약 / 중 / 강 |

"왜 하필 10%냐"는 질문이 성립하지 않게 된다.

### 5.6 반올림 소멸 처리 — 실측 23건

5.2의 둘째 자리 반올림 결과, **0.1% 주입 시 차이가 소멸하는 건이 발생한다.**

| 주입 비율 | 소멸 건수 |
|---|---|
| **0.1%** | **23건** (하자 989건 중 2.3%) |
| 1% / 10% / 50% | 0건 |
| 기한 1/3/7/30일 | 0건 |
| 명칭 약/중/강 | 0건 |

```
1.09 × 1.001 = 1.09109  →  반올림 1.09  →  원본과 동일
```

**하자를 심으려다 실패한 것이다.** 두 값이 실제로 같으므로 하자가 아니다.
그런데 정답지에는 "하자"로 적혀 있으니 **정답지가 사실과 어긋난다.**

이대로 두면 모델이 완벽히 읽어도 "못 잡았다"로 집계되어,
소액 구간에서만 성능이 낮게 나오는 가짜 결론이 생긴다.

#### 처리

```
1. 0.1% 주입
2. 원본과의 차이가 eps(0.01) 이하인지 확인
3. 이하이면 → 그 건의 정답지를 "정상"으로 수정
4. 건수 기록
```

**고치는 것은 정답지이며, 모델 출력이 아니다.**

#### 시점이 중요하다

| | 시점 | 판정 |
|---|---|---|
| **본 처리** | 모델 실행 **전** | 정당 |
| (금지) | 모델 실행 **후** 결과를 보고 수정 | 부정 |

코드에서 순서를 고정한다.

```
1. 정답지 생성        ← 23건 여기서 정리
2. 정답지 파일 저장   ← 확정. 이후 수정 금지
3. 모델 실행
4. 채점
```

#### 조건별로 정답지가 다르다

```
0.1% 조건 → 23건은 "정상"
1% 조건   → 23건도 "하자"  (차이가 살아남음)
```

같은 송장이라도 조건에 따라 정답이 다르다. 데이터가 실제로 그러하기 때문이다.

#### 이 자체가 결과다

> 금액이 작으면 0.1% 차이는 소수 둘째 자리로 표현되지 않는다

어느 모델을 써도 못 잡는다. 읽기 문제가 아니라 **표현 한계**다.

## 6. 층화 및 표본

### 6.1 자릿수 층화의 위치

금액 자릿수는 **결과 항목이 아니라 샘플링 장치**로만 쓴다.

브리핑 9절이 요구하는 조건별 기준선의 축은 **월 서류 건수**이지 금액 자릿수가 아니다.
자릿수별 탐지율 표를 결과로 내는 것은 브리핑에 없는 항목이므로 설계에 포함하지 않는다.

다만 결과 파일에 건별 금액이 그대로 저장되므로,
**실험을 다시 돌리지 않고도 사후에 금액대별로 갈라볼 수 있다.**
뚜렷한 차이가 나타나면 그때 README 수록 여부를 판단한다.

- 금액 **5분위**로 층화한 뒤 구간을 번갈아 뽑아 실행 순서를 만든다
  → 중간에 끊겨도 그때까지의 분량이 전 구간 대표성을 가진다
- **50장마다 결과를 파일에 기록**해 세션이 끊겨도 이어서 돌릴 수 있게 한다

실제 사용한 표본 수는 README에 그대로 기재한다 (브리핑 13절).

## 9. README 반영 문구

> 정답 데이터는 일반 상업 인보이스이며 신용장 부속 상업송장이 아니다.
> 사용한 표본은 정답이 존재하는 1,413장이다. 공표된 1,489장 중 batch1_2의 75장은
> 정답이 존재하지 않아, 파일명이 중복된 1장은 중복으로 제외했다.
> batch_2·3은 정답이 없어 제외했다.
>
> 금액 표기는 점을 소수점으로 쓰는 건(1,078)과 쉼표를 소수점으로 쓰는 건(336)이
> 섞여 있으며 천 단위는 공백으로 구분된다. 초기 파싱에서 쉼표를 제거해
> 336건이 100배로 집계되는 오류가 있었고, 모델 실행 전에 수정했다.
>
> 선적일 필드가 없어 기한 규칙은 송장 발행일을 대조 대상으로 삼았고,
> 마감일은 금액·명칭 조건과 마찬가지로 합성했다.
> 마감 간격은 UCP 600 제14조(c)의 21일 제시기간을 기준으로 설정했다.
> 이 데이터셋은 지급기한 필드가 전 건 비어 있어 데이터 교차확인은 하지 못했다.
>
> 하자 주입 비율은 ICC가 보고한 신용장 1차 제시 거절률 70%를 따랐다.
> 이는 최종 지급거절률이 아니라 1차 제시 단계의 수치다.
>
> 합성 조건 금액은 정답 데이터와 동일하게 소수점 둘째 자리로 반올림했다.
> 그 결과 0.1% 주입 시 23건에서 차이가 소멸해 정답지 생성 단계에서
> 정상으로 처리했다. 해당 금액대에서 0.1% 차이는 소수 둘째 자리로 표현되지 않는다.
>
> UCP 600의 엄격일치 원칙은 1일·1원 차이도 하자로 보지만, 본 실험은 파싱 정확도를
> 분리해 측정하기 위해 금액은 0.1/1/10/50%, 기한은 1/3/7/30일, 명칭은 약/중/강으로
> 나누어 각각 측정했다. 실제 심사 기준보다 완화된 조건이다.
