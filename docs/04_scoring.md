## 2. 공정성 장치 ★

브리핑 5절의 핵심 요건이다.

```
granite_raw.jsonl  (DocTags)  ──┐
                                 ├→ 동일한 추출기 하나 → 필드값
paddle_raw.jsonl   (OTSL)     ──┘
```

모델별 추출기를 따로 짜면 **"어느 쪽 파서를 더 잘 짰나"가 결과에 섞인다.**
브리핑이 3층에 Granite Vision을 두지 말라고 한 것과 같은 문제다.

### 3단계에서 이미 대비했다

프롬프트를 `Table Recognition:`으로 고른 이유가 이것이다.
양쪽 모두 `<fcel>` `<lcel>` `<nl>` 태그를 쓴다.

## 3. 실제 출력 구조 (batch1-0182 기준)

### 3.1 공통 태그

| 태그 | 의미 | Granite | Paddle |
|---|---|---|---|
| `<fcel>` | 데이터 칸 | 있음 | 있음 |
| `<ched>` | 머리글 칸 | 있음 | 없음 (`<fcel>`로 통일) |
| `<rhed>` | 행 머리글 | 있음 | 없음 |
| `<lcel>` | 병합된 빈 칸 | 드묾 | 많음 |
| `<ecel>` | 빈 칸 | 있음 | 있음 |
| `<nl>` | 행 구분 | 있음 | 있음 |
| `<loc_NNN>` | 좌표 | **있음** | **없음** |
| `<otsl>` `<text>` `<doctag>` | 구조 태그 | **있음** | **없음** |

### 3.2 총액 — 구조 거의 동일

**Granite**
```
<section_header_level_1>SUMMARY</section_header_level_1>
<otsl><ecel><ched>VAT [%]<ched>Net worth<ched>VAT<ched>Gross worth<nl>
      <rhed>10%<fcel>115,74<fcel>11,57<fcel>127,31<fcel>Total<nl></otsl>
```

**Paddle**
```
<fcel>SUMMARY<lcel>...<nl>
<ecel><lcel><fcel>VAT [%]<lcel><fcel>Net worth<fcel>VAT<fcel>Gross worth<lcel><nl>
<ecel><lcel><fcel>10%<lcel><fcel>115,74<fcel>11,57<fcel>127,31<lcel><nl>
<fcel>Total<lcel><lcel><lcel><fcel>$ 115,74<fcel>$ 11,57<fcel>$ 127,31<lcel><nl>
```

**차이 둘**

1. Paddle은 `Total` 행이 한 줄 더 있고 금액에 `$` 기호가 붙는다
2. Granite는 `Total`이 같은 행의 마지막 칸에 들어간다

→ 통화기호를 제거하고, SUMMARY 이후 모든 행에서 **최대 금액**을 취한다.

### 3.3 날짜 — 동일

```
Granite   <text>Date of issue:</text><text>10/02/2020</text>
Paddle    <fcel>Date of issue:<lcel><lcel><fcel>10/02/2020<lcel>...<nl>
```

### 3.4 상호 — 구조가 다르다 ★

```
Granite   Campbell, Chavez and Reynolds 462 Lewis Manor Apt. 741 Richardfurt, IL 50521
                                        ↑ 이름과 주소가 한 덩어리 (구분자 없음)

Paddle    Campbell, Chavez and Reynolds\n462 Lewis Manor Apt. 741\nRichardfurt, IL 50521
                                        ↑ \n 으로 분리됨
```

**이 지점이 공정성의 최대 위험 구간이다.**

`\n` 기준 추출기를 쓰면 Paddle은 쉽게 처리되고 **Granite만 일방적으로 손해**를 본다.

#### 채택 규칙 — 양쪽에 동일하게 작동

```
"주소 시작 지점 앞에서 자른다"
  · 숫자로 시작하는 토큰 (번지수)
  · 주소 키워드 (PSC, USNV, Unit, Box 등)
```

`\n`은 공백으로 정규화한 뒤 이 규칙을 적용한다.
**한 규칙이 양쪽에서 같은 결과를 낸다.**

## 4. 추출 대상

| 필드 | 위치 | 정답 키 |
|---|---|---|
| 금액 | SUMMARY 표의 Gross worth | `subtotal.total` |
| 날짜 | 헤더의 Date of issue | `invoice.invoice_date` |
| 상호 | Seller 블록 (**왼쪽**) | `invoice.seller_name` |

**상호 주의**: 오른쪽 블록은 고객(`client_name`)이다.
2단계 검증에서 `Campbell, Chavez and Reynolds`가 판매자,
`Rodriguez-Morgan`이 고객임을 확인했다.

Paddle 출력에서는 한 행에 판매자와 고객이 나란히 들어간다.

```
<fcel>Campbell...<lcel><lcel><fcel>Rodriguez-Morgan...<lcel>...<nl>
      ↑ 왼쪽 = 판매자        ↑ 오른쪽 = 고객
```

→ `Seller:` 관련 행의 **첫 번째** 셀 내용을 취한다.

## 5. 추출 규칙

### 5.1 공통 전처리

```
1. 좌표 태그 제거              <loc_\d+>     (Granite만)
2. 구조 태그 제거              <doctag> <otsl> </otsl> <|end_of_text|>
3. 셀 태그를 구분자로 치환     <fcel> <ched> <rhed> <ecel> → SEP
4. 병합 칸 제거                <lcel>
5. 행 분리                     <nl> 및 <text>...</text> 단위
6. \n → 공백 정규화
```

### 5.2 금액

```
"SUMMARY" 이후 영역을 잘라냄
→ 'Tax Id' / 'IBAN' 이 나오면 절단
→ 모든 셀에서 금액 패턴 수집 (소수점 두 자리 필수)
→ parse_amount() 로 변환
→ 최대값 채택 (Gross worth = Total)
```

**`parse_amount()`는 1단계에서 확정한 함수를 그대로 쓴다.**
천 단위 = 공백, 소수점 = 점 또는 쉼표.
2·3단계 출력 모두 `115,74` `127,31` 형태가 확인됐다.

### 5.3 날짜

```
"Date of issue" 인근에서 MM/DD/YYYY 탐색
→ 실패 시 전체에서 첫 번째 날짜 패턴
```

### 5.4 상호

```
(b) 'Seller: 이름 주소...' 가 한 칸에 있는 경우 → 접두사 제거 후 추출
(a) 'Seller' 행 → 다음 행의 첫 셀
(c) 같은 행의 다음 칸
→ 3.4의 절단 규칙 적용
→ Tax Id / IBAN / 표 머리글은 건너뜀
```

## 6. 채점 기준

| 필드 | 일치 판정 |
|---|---|
| 금액 | `amount_matches(추출값, 정답, eps=0.01)` |
| 날짜 | 문자열 완전 일치 |
| 상호 | `name_matches(추출값, 정답, strict=True)` |

**`rules.py`의 함수를 그대로 쓴다.**
`amount_matches`는 0단계에서 BPI 8,564건으로 검증된 함수다.

### 추출 실패와 오추출 구분

| 상태 | 의미 |
|---|---|
| `extracted` | 값을 뽑아냈는가 |
| `correct` | 뽑은 값이 정답과 같은가 |

```
못 뽑음        → extracted=False, correct=False
뽑았으나 틀림  → extracted=True,  correct=False
맞음           → extracted=True,  correct=True
```

**둘을 구분해야 "못 읽은 것"과 "잘못 읽은 것"이 갈린다.**

## 8. 결과 — 축 1 (2026-09-23)

### 8.1 필드별 정확도 (n=150)

| | 금액 | 날짜 | 상호 |
|---|---|---|---|
| **Granite Docling** | 98.0% | 100.0% | 100.0% |
| **PaddleOCR-VL** | 98.0% | 100.0% | 100.0% |
| **차이** | **0.0p** | **0.0p** | **0.0p** |

추출 성공률은 세 필드 모두 양쪽 100%. 못 읽은 건은 없다.

**세 필드 전부 동률이다.**

### 8.2 금액 오답 3건 — 모델 오류가 아님

| 파일 | 추출값 | 정답 `total` | 정답 `tax` | 관계 |
|---|---|---|---|---|
| batch1-0864 | 893.82 | 812.56 | 81.26 | 812.56 + 81.26 = 893.82 |
| batch1-1046 | 686.02 | 623.65 | 62.37 | 623.65 + 62.37 = 686.02 |
| batch1-0167 | 95.22 | 86.56 | 8.66 | 86.56 + 8.66 = 95.22 |

**두 모델이 완전히 동일한 값을 냈다.** 모델 차이라면 나올 수 없는 결과다.

원인은 정답 JSON의 필드 의미 불일치다.

```
147건 : total = Gross worth (세후)   ← 다수
  3건 : total = Net worth   (세전)   ← 소수
```

기준 검증에 쓴 `batch1-0182`는 `total = 127.31 = Gross`였다.
모델은 일관되게 Gross를 읽었고, 이 3건만 정답 쪽이 Net이다.

**처리**: 정답지를 수정하지 않는다.
결과를 본 뒤 정답을 바꾸면 검증의 의미가 사라진다.
두 모델이 동일하게 손해를 보므로 비교에는 영향이 없다.

**실질 추출 정확도는 양쪽 100%다.**

## 9. 추출기 수정 이력 ★

추출기를 세 차례 고쳤다. **모두 양쪽 모델에 동일하게 적용되는 규칙**이며,
한쪽만 유리하게 만드는 변경은 하지 않았다.

### 9.1 금액 — 정수 오인 (Granite만 피해)

```
Granite: 33798.0  vs  정답 127.31
```

`33798`은 고객 주소의 우편번호였다.

두 모델의 출력 순서가 다르다.

```
Granite : SUMMARY 표 → 고객 주소 블록
Paddle  : 고객 주소 → SUMMARY 표
```

SUMMARY 이후를 무제한으로 훑으면 Granite에서만 주소가 범위에 들어간다.

**수정 둘**
- 금액 정규식에 소수점 두 자리 필수화 (`[.,]\d{2}(?!\d)`)
  → 우편번호·번지수·Tax Id를 금액으로 오인하지 않는다
- `Tax Id` / `IBAN` 이 나오면 탐색 범위 절단

### 9.2 상호 — 주소 절단 실패 (양쪽 피해, 43건)

```
Granite  'Mcdonald LLC PSC'                     vs  'Mcdonald LLC'
Granite  'Glover, Harvey and Davis USNV Miller' vs  'Glover, Harvey and Davis'
Paddle   'Johnson, Buckley and Terry Unit'      vs  'Johnson, Buckley and Terry'
```

초기 규칙은 "숫자로 시작하는 토큰 앞에서 자른다"였다.
미국 주소가 번지수로 시작한다는 가정이었으나,
군사우편·함정·부대 주소는 **문자로 시작**한다.

```
PSC 1234 Box 5678
USNV Miller, FPO AE 09876
Unit 1234 Box 5678
```

**수정**: `_ADDR_START` 집합 도입
(`psc`, `fpo`, `apo`, `usnv`, `usns`, `uss`, `uscgc`, `unit`, `box`, `apt`, `suite` 등)

→ Granite 24건, Paddle 19건 동시 개선.

### 9.3 상호 — 출력 형태 차이 (Paddle만 피해, 3건)

Paddle 출력 중 일부는 `Seller:` 와 이름이 **한 칸에** 들어 있다.

```
'Seller: Hayes-Mcdonald 6220 Hughes Isle East Charlesmouth, NM 82727 Tax Id: ...'
```

초기 코드는 "`Seller` 행 → 다음 행에서 이름"만 처리했고,
`_SKIP`에 `seller`가 있어 해당 칸을 건너뛰어 `None`이 됐다.

**수정**: `_SELLER_PREFIX` 도입.
`Seller:` 접두사를 제거하고 나머지에서 이름을 추출하는 경로를 추가했다.
`_SKIP`에서 `seller`를 제거했다.

### 9.4 수정 판단 기준

```
양쪽 모두 겪는 구조적 오류      → 수정
한쪽만 손해 보는 규칙을 채택     → 하지 않음
결과를 보고 한쪽에 맞춰 조정     → 하지 않음
```

9.1은 Granite만, 9.3은 Paddle만 피해였으나
**둘 다 추출기 결함이지 모델 성능이 아니다.**
방치하면 해당 모델의 점수가 부당하게 깎인다.

각 수정 후 양쪽 점수 변화를 기록했다.

| 단계 | Granite 상호 | Paddle 상호 |
|---|---|---|
| 초기 | 84.0% | 85.3% |
| 주소 키워드 추가 후 | 98.0% | 96.0% |
| Seller 접두사 처리 후 | **100.0%** | **100.0%** |

## 10. 해석

### 10.1 브리핑 예상과 다른 결과

브리핑 13절은 이렇게 보았다.

> PaddleOCR-VL이 벤치마크 1위라 질 가능성이 높다. 결과를 그대로 쓸 것.

**질 가능성을 우려했으나, 이기지도 지지도 않았다.**

### 10.2 왜 동률인가

이 데이터는 **합성 송장**이다. 글씨가 깨끗하고 양식이 일정하다.
258M 모델로도 충분히 읽힌다.

OmniDocBench v1.6 1위(96.33%)는 손글씨·저화질·복잡 레이아웃을
포함한 종합 점수다. **그런 난이도가 아닌 문서에서는 격차가 드러나지 않는다.**

### 10.3 축 2로 결론이 넘어간다

브리핑 9절이 두 축을 둔 이유가 여기서 드러난다.

| 축 | 결과 |
|---|---|
| 축 1 (성능) | **동률** |
| 축 2 (배포 부담) | 258M vs 0.9B — **3.5배** |

성능 차이가 없다면 선택 기준은 배포 부담으로 넘어간다.

### 10.4 한계 명시

이 결과는 **정형화된 합성 송장 150장**에 대한 것이다.

- 손글씨, 스캔 노이즈, 비정형 레이아웃은 포함되지 않았다
- 실제 무역서류(신용장 부속 상업송장)가 아니다
- 표본 150장은 1~2%p 차이를 변별하기에 충분하지 않다

README에 그대로 기재한다.

## 12. README 반영 문구

> 두 모델의 출력에 **동일한 추출기 하나**를 적용했다. 모델별 파서를 따로 만들면
> 파서 품질 차이가 결과에 섞이기 때문이다. 3단계에서 PaddleOCR 프롬프트를
> `Table Recognition:`으로 고른 것도 Granite와 같은 OTSL 태그 체계를 얻기 위해서였다.
>
> 정형화된 합성 송장 150장에서 금액·날짜·상호 세 필드의 추출 정확도는
> 두 모델이 동일했다(98.0% / 100.0% / 100.0%). 금액 오답 3건은 두 모델이
> 같은 값을 냈으며, 정답 JSON의 `total`이 세후가 아닌 세전 금액인 건이다.
> 데이터셋의 표기 불일치이며 모델 오류가 아니다. 정답지는 수정하지 않았다.
>
> 추출기는 세 차례 수정했다. 금액에서 우편번호를 오인하는 문제(Granite 피해),
> 군사우편 주소를 절단하지 못하는 문제(양쪽 43건), `Seller:`와 이름이 한 칸에
> 들어간 출력 형태(Paddle 피해)였다. 모두 추출기 결함이지 모델 성능이 아니며,
> 각 수정은 양쪽 모델에 동일한 규칙으로 적용했다.
>
> 이 결과는 정형화된 합성 송장에 대한 것이다. 손글씨·스캔 노이즈·비정형
> 레이아웃은 포함되지 않았고, 표본 150장은 1~2%p 차이를 변별하기에 충분하지 않다.

## 13. 다음 단계

5단계에서 추출값에 규칙 3종을 적용해 하자 탐지율로 환산한다.

**축 1이 동률이므로 탐지율·오탐률도 동률로 나올 것이 예상된다.**
그럼에도 수행하는 이유는 둘이다.

1. 브리핑 5절의 "파싱 정확도가 탐지율로 환산됨"을 실물로 보이기 위해
2. 6단계 손익분기 계산에 `r`(탐지율), `p`(오탐률) 값이 필요하기 때문
