---

## 1. 왜 추가했는가

4·5단계에서 두 모델이 완전히 동률로 나왔다.
추출값 450개 중 449개가 같았고, 유일한 차이도 대소문자였다.

원인은 **채점 범위가 좁았기 때문**일 수 있다.

```
모델이 뱉은 것     페이지 전체 (헤더·주소·품목표·SUMMARY)
채점한 것          금액·날짜·상호 세 값만
```

3단계 확인 때 **채점하지 않은 영역에서는 차이가 있었다.**

```
Granite   ... OVER TAUPE LONG DRESS
Paddle    ... OVER TAUPF LONG DRESS
                    ↑ E vs F
```

## 2. 정답 자료

Kaggle CSV의 **`OCRed Text`** 컬럼 — 송장 원문 텍스트.
지금까지는 `Json Data`(구조화 정답)만 썼다.

## 3. 공정성 — 동일한 평탄화

```
granite_raw.jsonl  (DocTags)  ──┐
                                 ├→ to_rows() → 평문 → 정답과 대조
paddle_raw.jsonl   (OTSL)     ──┘
```

`extract_fields.py`의 `to_rows()`를 그대로 쓴다.
4단계에서 세 필드를 뽑을 때와 **같은 전처리**다.

대소문자·공백·통화기호도 양쪽 동일하게 정규화한다.

---

## 4. 두 가지 기준으로 측정한 이유 ★

초기에는 순서를 반영하는 `SequenceMatcher` 하나만 썼다.
그 결과가 이랬다.

```
숫자 재현율   granite 55.15%   paddle 73.00%   차이 -17.85p
건별 승패     paddle 150승 0패
```

**150전 150패는 성능 차이보다 구조적 편향의 모양이다.**
게다가 4단계와 모순된다. 같은 출력인데 세 필드는 동률, 전체는 17.85p 차이다.

### 4.1 원인 — 출력 순서

2단계에서 확인한 배치다.

```
Granite   헤더 → 판매자 → ITEMS → SUMMARY → 고객 주소   ← 고객이 맨 끝
Paddle    헤더 → 판매자·고객 → ITEMS → SUMMARY          ← 시각적 순서
정답      눈으로 읽는 순서 (위→아래)                     ← Paddle과 일치
```

정답 텍스트가 시각적 읽기 순서이므로,
순서 기반 비교는 **Granite를 일방적으로 불리하게 만든다.**

### 4.2 해결 — 지표 분리

| 함수 | 방식 | 재는 것 |
|---|---|---|
| `prf()` | difflib, 순서 반영 | 읽기 순서 충실도 |
| `bag()` | 다중집합 교집합, 순서 무시 | **내용 인식 정확도** |

**둘을 나눈 것 자체가 결과다.** 차이가 어디서 오는지 분해된다.

---

## 5. 결과 (2026-09-24, n=150)

### 5.1 모델별 평균

| 지표 | Granite | Paddle | 차이 |
|---|---|---|---|
| 문자 유사도 | 75.22% | 78.40% | -3.19p |
| 토큰 재현 (순서) | 72.21% | 78.01% | -5.80p |
| **숫자 재현 (순서)** | **55.15%** | **73.00%** | **-17.85p** |
| 토큰 재현 (무순) | 94.41% | 96.92% | -2.51p |
| **숫자 재현 (무순)** | **79.06%** | **83.25%** | **-4.18p** |
| 숫자 정밀 (무순) | 80.48% | 83.35% | -2.88p |

### 5.2 읽기 순서의 영향

| 모델 | 순서 반영 | 순서 무시 | 손실 |
|---|---|---|---|
| Granite | 55.15% | 79.06% | **-23.92p** |
| Paddle | 73.00% | 83.25% | -10.25p |

```
모델 간 차이   순서 반영 -17.85p   순서 무시 -4.18p
               ↓
    차이의 13.67p (77%)가 순서 때문
```

**Granite가 순서로 잃는 양이 Paddle의 2.3배다.**

### 5.3 건별 승패 (순서 무시 숫자 재현율)

```
granite 우세    0건
paddle  우세   78건
동점           72건
```

**Granite가 이기는 건이 하나도 없다.**
절반은 동점, 나머지는 Paddle 우세다.
Paddle이 놓치는 것을 Granite가 잡는 경우는 없었다.

---

## 6. 무엇을 놓치는가 — 누락 항목 분석

Paddle 100%, Granite 65.2%로 격차가 가장 컸던 `batch1-0843`을 열었다.

```
정답 숫자 23개
Granite  20개 인식  →  누락 8개
Paddle   25개 인식  →  누락 0개 (정답보다 2개 많음, 표 구조상 중복)
```

**Granite가 누락한 숫자**

```
9991001099        Tax Id
94800, 10858      우편번호
981, 84, 1838     번지수
```

**전부 주소와 Tax Id다.** 금액도, 품목 수량도, 날짜도 아니다.

Granite가 고객 주소 블록을 덜 뽑았다.
4.1의 순서 문제와 **같은 뿌리**다. 고객 정보를 맨 뒤로 몰면서 일부를 누락했다.

### 6.1 우리 규칙과의 관계

| 영역 | Granite | Paddle | 우리 규칙 대상 |
|---|---|---|---|
| 금액·날짜·상호 | 100% | 100% | **예** |
| 품목 표 | 읽음 | 읽음 | 아니오 |
| 고객 주소·Tax Id | **일부 누락** | 읽음 | **아니오** |

**우리가 쓰는 세 필드는 둘 다 완벽하다.** 차이는 그 바깥에 있다.
신용장 심사에서 고객 주소와 Tax Id는 대조 항목이 아니며,
규칙 3종(금액·기한·명칭)에도 포함되지 않는다.

### 6.2 토큰은 94%인데 숫자는 79%

```
토큰 재현 (무순)   granite 94.41%   paddle 96.92%
숫자 재현 (무순)   granite 79.06%   paddle 83.25%
```

**두 모델 다 숫자에서 15%p 이상 떨어진다.**
송장은 표에 숫자가 빽빽하고, 이 데이터는 쉼표 소수점(`115,74`)까지 섞여 있다.
숫자가 문자보다 어렵다는 것은 양쪽에 공통이다.

## 7. 결론 — 세 층의 판단 기준선 ★

| 층위 | Granite | Paddle | 차이 |
|---|---|---|---|
| **세 필드 (실무 지표)** | 100% | 100% | **0.0p** |
| 페이지 전체 숫자 (내용) | 79.06% | 83.25% | -4.18p |
| 페이지 전체 숫자 (순서) | 55.15% | 73.00% | -17.85p |

**해석이 셋 다 다르다.**

```
필요한 필드만 뽑아 쓰면       →  차이 없음. 258M으로 충분
페이지 전체를 인덱싱하면      →  Paddle 4%p 우세
위치 기반 후처리를 하면       →  Paddle 크게 우세
```

브리핑 2절이 요구한 **"조건별 판단 기준선"**이 이 모양이다.
"누가 낫다"가 아니라 **"무엇을 하려는지에 따라 다르다"**가 답이다.

## 8. 한계

- `OCRed Text`는 데이터셋 제작자가 생성한 것으로, 그 자체가 완벽하지 않을 수 있다
- Paddle이 정답보다 숫자를 더 많이 출력하는 건이 있다(표 구조상 중복). 정밀도 지표로 보완했다
- 이 지표는 참고용이다. **실무 지표는 세 필드 정확도다**
- 정형화된 합성 송장 150장에 대한 결과다

## 10. README 반영 문구

> 세 필드가 동률로 나온 뒤, 채점 범위를 페이지 전체로 넓혀 보조 측정을 했다.
> 정답은 데이터셋의 `OCRed Text` 컬럼이며, 평탄화는 4단계와 같은 함수를 썼다.
>
> 초기 측정에서 숫자 재현율이 17.85%p 차이로 나왔으나, 이 중 13.67%p가
> **읽기 순서 때문**이었다. Granite Docling은 고객 주소 블록을 출력 맨 뒤에
> 배치하는데, 정답 텍스트는 시각적 읽기 순서라 순서 기반 비교에서 일방적으로
> 불리해진다. 순서를 무시한 다중집합 비교로 다시 재자 차이가 4.18%p로 줄었다.
>
> 남은 4.18%p는 실제 인식 차이다. 격차가 가장 큰 건을 열어보니 Granite가
> 누락한 것은 Tax Id·우편번호·번지수로, **전부 고객 주소 영역**이었다.
> 금액·품목 수량·날짜는 누락이 없었다. 우리가 대조하는 세 필드는 양쪽 모두 100%다.
>
> 결론은 용도에 따라 갈린다. 필드 단위로 뽑아 쓰면 258M으로 충분하고,
> 페이지 전체를 텍스트로 인덱싱하거나 위치 기반 후처리를 한다면 0.9B가 낫다.
>
> 두 모델 모두 토큰 재현율은 94~97%인데 숫자 재현율은 79~83%로 떨어졌다.
> 표에 숫자가 밀집하고 쉼표 소수점 표기가 섞인 문서에서는 숫자가 문자보다 어렵다.
