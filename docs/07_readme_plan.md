## 2. 제목과 한 줄 요약 ★

**측정 보고서가 아니라 판단 보고서로 읽히게 한다.**

```markdown
# 어느 고객에게 어느 모델을 권할 것인가
### 무역금융 서류 파싱 — Granite Docling vs PaddleOCR-VL

신용장 부속서류를 은행 내부 서버에서 읽어낼 파싱 모델 두 개를
같은 조건에서 측정하고, **어떤 고객 상황에 어느 쪽이 맞는지**
판단 기준선을 냈다.

결론부터: **두 모델의 성능은 같았고, 선택을 가르는 것은 모델이 아니었다.**
```

### 이 구성의 근거

| 요소 | 역할 |
|---|---|
| 제목이 질문 형태 | "벤치마크 보고서"가 아니라 "판단한 사람"으로 읽힘 |
| 부제에 모델명 | **실제로 돌렸다**는 사실을 보증. 브리핑 12절 대응 |
| 마지막 줄 | "모델을 비교했는데 모델이 중요하지 않았다" — 읽는 사람을 멈춰 세움 |

### 금지 표현 (브리핑 12절)

| ❌ | ✅ |
|---|---|
| 문서 자동화 플랫폼을 만들었다 | **파싱 모델의 추출 정확도를 검증했다** |

IBM에 Datacap/CP4BA가 있어 "우리 제품과 뭐가 다르냐"는 질문을 받는다.
제목을 영업 쪽으로 밀되, **측정 사실이 부제에서 유지되어야 한다.**

## 4. 결론 — 먼저 쓴다

브리핑 9절의 두 축을 문장으로 만든다.

### 축 1 — 성능

```markdown
정형화된 상업 송장 150장에서 금액·날짜·상호 세 필드의 추출 정확도는
두 모델이 동일했다 (98.0% / 100% / 100%).

채점 범위를 페이지 전체로 넓히면 PaddleOCR-VL이 숫자 재현율에서
4.18%p 앞섰다. 다만 Granite가 누락한 것은 고객 주소와 Tax Id로,
신용장 대조 항목이 아니었다.
```

### 축 2 — 배포 부담

```markdown
Granite Docling 258M (515MB) vs PaddleOCR-VL 0.9B (1.92GB).
모델 크기 3.5배 차이.

다만 처리 속도는 PaddleOCR이 빨랐다 (18.0초 vs 26.3초, T4 기준).
브리핑 단계에서는 PaddleOCR이 페이지 단위 파싱을 지원하지 않아
다중 호출이 필요할 것으로 보았으나, 실측 결과 한 번 호출로 처리됐다.
```

### 최종 문장

```markdown
필드 단위로 뽑아 쓰면 258M으로 충분하다.
페이지 전체를 인덱싱하거나 위치 기반 후처리를 한다면 0.9B가 낫다.

도입 여부는 모델 성능이 아니라 운영비가 재제출 비용의 몇 배인가가 결정한다.
```

> 브리핑 9절 원문은 "월 N건 이상이면 Granite 탐지율로도 손익분기를 넘는다"였다.
> 절대 금액을 알 수 없어 단일 숫자를 쓸 수 없으므로 비율 형태로 바꿨다.

## 5. 대문 표 — "무엇이 결정하는가" ★

### 5.1 손익분기 표를 그대로 걸지 않는 이유

```
Granite   탐지율 100%, 오탐률 2.5%  →  손익분기 15건
Paddle    탐지율 100%, 오탐률 2.5%  →  손익분기 15건
                                       ↑ 완전히 같음
```

손익분기 표를 대문에 걸면 읽는 사람이 **"이게 Granite의 강점인가"**로 읽는다.
그런데 아니다. 어느 모델을 써도 같다.

게다가 첫 화면에서 "재제출 10건 값이 얼마인데요?"를 묻게 된다.
**모르는 값 두 개를 첫 줄에서 물리면 안 된다.**

### 5.2 채택안 — 민감도 표

```markdown
## 무엇이 도입 여부를 결정하는가

| 요인 | 손익분기에 미치는 영향 |
|---|---|
| 운영비 / 재제출비 비율 | 10배 → 15건, 100배 → 150건 |
| 재제출 1회 비용 | 4배 → 필요 건수 1/4 |
| 모델 탐지율 | 20%p 하락 → 4건 차이 |
| 모델 오탐률 | 20배 증가 → **변화 없음** |

**모델 성능이 아니라 비용 구조가 결정한다.**
```

**위에서 아래로 갈수록 영향이 작아진다.** 맨 아래 두 줄이 모델 이야기다.

이것이 브리핑 2절의 "조건별 판단 기준선"이며,
**"모델 고르는 게 중요한 게 아니다"**가 첫 화면에 나온다.

### 5.3 손익분기 표는 그 아래에 둔다

```markdown
| 월 운영비 (재제출 M건 값) | 손익분기 |
|---|---|
| 5 | 8건 |
| 10 | 15건 |
| 50 | 75건 |
| 100 | 150건 |

재제출 1회 비용에는 재작성 인건비뿐 아니라
은행 재심사 대기 5영업일(UCP 600)의 기회비용이 포함된다.
5영업일 지연이 자금 회전에 치명적인 중소 수출기업일수록
손익분기가 낮아진다.
```

## 6. 판단의 연쇄 — 단계 나열이 아니다 ★

```markdown
## 어떻게 판단했나

규칙을 먼저 검증하고, 그 규칙으로 모델을 쟀다.

**1. 규칙이 맞는지 먼저 확인**
BPI Challenge 2019 실데이터 8,564건으로 금액 대조 규칙을 검증했다.
규칙 출력이 정의상 정답과 100% 일치했고,
허용오차를 0.001~10 EUR로 바꿔도 판정이 변하지 않았다.

**2. 정답지를 모델 실행 전에 확정**
조건별 정답지 9개를 만들어 파일로 굳힌 뒤 모델을 돌렸다.
결과를 보고 정답을 고칠 여지를 없앴다.

**3. 두 모델을 같은 조건에서 실행**
같은 150장, 같은 순서. 프롬프트는 양쪽 5개씩 비교해 최선값을 채택했다.

**4. 하나의 추출기로 채점**
모델별 파서를 따로 만들면 파서 품질이 결과에 섞인다.

**5. 검증된 규칙을 적용해 탐지율로 환산**

**6. 탐지율을 비용 수식에 대입**
```

**각 단계가 "왜 그렇게 했는가"를 달고 있다.**
단순 나열보다 판단력이 드러난다.

## 7. 공정성 장치 — 이게 핵심이다

**"IBM 모델이 이기게 만들지 않았다"를 보여주는 절.**
읽는 사람이 가장 의심할 지점이다.

```markdown
## 공정성을 어떻게 지켰나

두 모델의 출력에 **동일한 추출기 하나**를 적용했다.

PaddleOCR 프롬프트를 `Table Recognition:`으로 고른 것도
Granite와 같은 OTSL 태그 체계를 얻기 위해서였다.
값의 정확도가 아니라 출력 형식 때문에 고른 것이다.

### 추출기 수정 이력

| 문제 | 피해 | 수정 |
|---|---|---|
| 우편번호를 금액으로 오인 | Granite | 소수점 두 자리 필수화 |
| 군사우편 주소 절단 실패 | 양쪽 43건 | 주소 키워드 추가 |
| `Seller:`와 이름이 한 칸에 | Paddle | 접두사 처리 경로 추가 |

한쪽만 손해 보는 규칙은 채택하지 않았다.
각 수정 후 양쪽 점수 변화를 기록했다.

| 단계 | Granite 상호 | Paddle 상호 |
|---|---|---|
| 초기 | 84.0% | 85.3% |
| 주소 키워드 추가 후 | 98.0% | 96.0% |
| Seller 접두사 처리 후 | 100.0% | 100.0% |
```

**이 표가 README에서 가장 값나가는 부분이다.**
결과보다 "어떻게 공정하게 쟀는가"가 이 직무의 증거다.

## 8. 결과 — 표로 압축

```markdown
## 결과

### 필드별 추출 정확도 (n=150)

| | 금액 | 날짜 | 상호 |
|---|---|---|---|
| Granite Docling | 98.0% | 100.0% | 100.0% |
| PaddleOCR-VL | 98.0% | 100.0% | 100.0% |

금액 오답 3건은 두 모델이 같은 값을 냈다.
정답 JSON의 `total`이 세후가 아닌 세전 금액인 건으로,
데이터셋 표기 불일치이며 모델 오류가 아니다.

### 하자 탐지율

탐지율 100%, 오탐률 2.5%로 두 모델 동일. 9개 조건 전부 차이 0.0%p.

주입 폭을 0.1%에서 50%로 500배 키워도 탐지율이 변하지 않았다.
**탐지율은 하자 크기가 아니라 파싱 정확도가 결정한다.**

### 페이지 전체 인식 (보조 지표)

| | 숫자 재현율 (순서 무시) |
|---|---|
| Granite | 79.06% |
| PaddleOCR | 83.25% |

Granite가 누락한 것은 Tax Id·우편번호·번지수로 전부 고객 주소 영역이었다.
금액·품목 수량·날짜는 누락이 없었다.
```

## 10. 한계 — 반드시 적는다 (브리핑 11절)

```markdown
## 한계

**데이터**
- 정형화된 합성 송장이다. 손글씨·스캔 노이즈·비정형 레이아웃은 없다
- 일반 상업 인보이스이며 신용장 부속 상업송장이 아니다
- 표본 150장은 1~2%p 차이를 변별하기에 충분하지 않다

**하자율**
- ICC가 보고한 70%는 **1차 제시 거절률**이며 최종 지급거절률이 아니다
- 이미 사람이 점검한 뒤의 값이다

**조건 합성**
- 선적일 필드가 없어 발행일을 대조 대상으로 썼다
- 마감일은 UCP 600 제14조(c)의 21일 제시기간으로 합성했다
- UCP 600 엄격일치는 1일·1원 차이도 하자로 보지만,
  파싱 정확도를 분리해 측정하기 위해 완화된 조건을 썼다

**비용 계산**
- 재제출 비용과 운영비의 절대 금액은 공개 자료가 없어 알 수 없다
- 두 값의 비율로 환원했을 뿐 불확실성이 사라진 것은 아니다
- 오탐이 많으면 담당자가 시스템을 불신해 결국 쓰지 않을 수 있다.
  비용이 아니라 채택의 문제이며 수식에 잡히지 않는다

**규칙 검증**
- 금액 규칙만 외부 실데이터로 검증했다
- 기한·명칭 규칙은 BPI 2019에 대응 필드가 없어 검증하지 못했다

**실행 환경**
- Tesla T4 단일 GPU, 배치 처리 없음
- A100/H100에서는 절대 시간이 다르다
```
